## Notes for the gate

- Task 1 missed criterion 1 as written, because no scenario was changed. The user's explanation (2026-11-04): reading them in a Markdown file may have played a part, and a formatted page may be easier to review. The user doesn't want to change the idea before trying the product while developing something. This is untested so far: task 1 was reviewed in Markdown and chat, not in the inbox. Task 2 is being reviewed in the inbox to test it.
- A third miss for task 1, found by the agent on 2026-11-04 while preparing the rendering variants: the fix for "every line is shown" still hid a tag such as `@manual` or a comment above a scenario, and showed a `Rule:` line inside the scenario before it. To be fixed with the chosen rendering.
- The user asked for variants of how the `.feature` text renders in the inbox, to pick one. They are on the throwaway branch `prototype/inbox-rendering`.
- First look at the real inbox with variants A to D (2026-11-04). The user changed no scenario's text yet, and raised three things about the product: (1) a glossary, ideally tied to OpenPurpose, that agents must keep to and ask a person to extend, with terms marked in the inbox; (2) all four variants are hard to read, a wall of text without white space or hierarchy, maybe use a next-next-next flow; (3) group use cases by vertical slice, such as billing or settings. None of this came up when reading Markdown. Whether it counts for criterion 1 is the user's call at the gate: it changes the product and how review works, not a scenario's behaviour.
- The glossary overlaps with what OpenPurpose already does, and the settled decisions say neither server calls the other and leave glossary links out of v1. That bears on the trial's "move into open-purpose" question.
- After variants E to G (2026-11-04): the user found F much easier to read and asked to combine it with E: start on the first scenario, go through with next and previous, and approve only after the last one. Ask for changes should need a comment. This reverses a choice the agent made alone in task 1 (asking for changes needed no comment), which the scenarios hadn't settled and the Markdown review hadn't caught. Written as UC-9. The user also said the Feature line isn't defined well enough. The user couldn't try Comment, because the agent had switched it off on the read-only copies.
- UC-9 approved with a change to S4, on 2026-11-04. The user didn't want "Ask for changes" locked behind a comment after all: it is always available and asks what should change in a dialog. The Feature complaint was about visibility: the `Feature:` line should leave or be clearer. The warning the agent added about a missing description worried the user and was removed.
- The user wasn't sure what "the gate" meant, because the agent had used the word without explaining it. Worth saying plainly from now on.
- The glossary decision (2026-11-04): it lives in OpenPurpose and applies only once a team adds that integration. This reopens "neither server calls the other". What to do without the integration was left to the agent: no terms are marked and everything else works the same (UC-7/S3).
