How it works

Running in five minutes.

  1. 1

    Run it

    Run it on your own server, then add a team, a project and an agent in Settings.

    terminal 
    $ git clone https://github.com/openstuff-dev/open-usecase
$ cd open-usecase && cp .env.example .env
$ docker compose up --build
  2. 2

    Connect your agent

    OpenUsecase is an MCP server, and it tells an agent the workflow when it connects. Ask for something a user can see. The agent proposes a use case and stops.

  3. 3

    Approve, and let CI prove it

    Approve it in the inbox and the agent builds it. Name tests with the scenario's ID, and CI turns the use case to done · passing.

Teams

Agents can't raise their rights

An agent can't manage tokens or permissions, not even its own.

Only people reject and retire

Admins manage the team. Members review. Agents and CI each have their own token.

Tokens shown once

Tokens are stored as hashes, and each one belongs to a single agent or CI job.

FAQ

Questions people ask first

Is it free?

Yes. OpenUsecase is open source under the MIT licence, so self-hosting costs nothing but your server.

Can I self-host it?

Yes, and for now that's the only way to run it. Docker Compose starts the app and Postgres, configured with environment variables.

Where is my data?

In your own Postgres. CI reports are read and thrown away, and you can export a team's data at any time.

Does every change need a use case?

No, only changes a user can see. Refactors, dependency bumps and CI need none. If an agent is unsure, it asks.

Which agents does it work with?

Any agent that speaks MCP. So far, we've run it with Claude Code. Test results come in as JUnit XML, which most test runners can write.

Can an agent get around it?

The server can prove that an approving token didn't write the use case, but it can't see who holds a token. A sub-agent normally counts as its parent. For a real second opinion, run the reviewer in CI with a token the proposing agent can't read.
